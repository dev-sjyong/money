# 개인회생 일정 관리 — Plan → Do → Check → Act

## Plan
- 두 사람의 이름/별칭별로 별도 계획, 종료일은 마지막 예정 회차로 계산.
- 기간·납부일·금액으로 월별 일정을 추가한 뒤 회차별 날짜/금액을 수정한다. 월말을 넘는 납부일은 해당 월 말일로 맞춘다.
- 회차마다 실제 납부일/금액을 여러 번 기록하여 부분 납부와 선납을 지원한다. 예정액 초과 납부는 차단하고 잘못된 납부 기록은 확인 후 제거한다.
- 예정 총액/실납부/잔여/연체/이번 달 예정액, 남은 회차/종료일까지 일수, 두 사람 합계 표시.
- 일정용 기록은 회계 원장에 자동 생성하지 않는다. 화면에서 안내해 중복 비용/부채 집계를 방지한다. 면책 여부를 자동 판정하지 않는다.
- Supabase RLS 구성원만 조회, RPC만 변경, household 잠금과 revision으로 동시 수정 충돌 감지. 정수 금액을 문자열/bigint로 처리.
- 기존 변경 유지, 신규 003 migration. 운영 SQL은 먼저 적용한 뒤 배포.

## Check
단위(월말·윤년·가변 금액·부분/선납·기한·정밀도), 실제 PostgreSQL(권한·입력·동시수정·원장 불변), 브라우저(두 계획·일정 편집·납부·재조회·모바일), 타입/빌드.

## 결과
- 신규 003 migration과 개인회생 일정 메뉴/편집 화면 구현. 가계부 구성원끼리 공유, 별도 회차/납부 기록 저장, 계획 보관/복원 지원.
- `npm test`: 기존 8 + 신규 3 = 11개 통과. 날짜·부분납부·선납·초과/음수/소수 금액·정밀도 검증.
- 타입검사와 프로덕션 빌드 통과.
- 실제 PostgreSQL 15에서 신규 32개 + 기존 105개 = 137개 검증 통과. RLS, 구성원 권한, 익명/타 가계부 차단, RPC만 쓰기, 충돌/잘못된 입력 원자적 거부, 회계 원장 불변 확인.
- 동시 수정 테스트: 같은 revision의 두 요청 중 하나만 성공하고 revision은 2, 회계 거래는 0건 유지.
- Chromium 브라우저 3개 시나리오 통과(기존 2 + 신규 1). 신규 시나리오는 두 사람의 다른 종료일/금액, 잘못된 입력, 중복 일정, 부분 납부, 재조회, 충돌 시 입력 보존, 보관, 320px/390px 화면 검사.
- 브라우저 테스트 중 발견한 기존 AmountInput의 포커스/전체 선택 간섭을 수정. 편집 중 표시값을 유지하고 blur에서 쉼표 표시. 기존 거래 복사/금액 변경 테스트도 통과.
- `repayment-mobile.png`를 육안 확인. 브라우저는 실제 앱 + 모의 Supabase HTTP 응답. 실제 원격 Auth/PostgREST/운영 migration은 미실행.

## 운영 반영 / Act
1. 001·002 적용된 Supabase SQL Editor에서 `supabase/migrations/202609300003_repayment.sql`만 전체 실행한다. 기존 migration과 테스트 bootstrap을 재실행하지 않는다.
2. SQL 성공 후 기능 PR을 main에 병합하여 Vercel에 반영한다.
3. 개인회생 일정에서 본인·배우자 계획을 각각 추가하고 기간/금액을 등록한 뒤 일정 저장. 납부 내역도 일정 저장을 눌러 반영한다.

전체 회차를 입력하면 원래 계획 전체를, 남은 회차만 입력하면 남은 일정만 관리한다. 회차 번호는 입력한 날짜 순서이다. 기존 납부 기록 자동 수집, 법원 연동, 면책 판정, 회계 거래 자동 생성은 하지 않는다. 원격 DB 인증정보가 없어 운영 SQL은 아직 실행하지 않았다.
